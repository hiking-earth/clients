## 八、启用路线目录自动同步到CloudBase（统一验收后再做）

开发端已在`.github/workflows/route-catalog-update.yml`加入默认关闭的部署门控。自动采集成功完成目录快照准备、目录提交与推送成功、且路线目录文件确有变化时，只有仓库变量`HIKING_CATALOG_AUTODEPLOY`严格等于`true`，工作流才会用CloudBase CLI部署`catalog-feed`和`client-api`；目录提交/推送失败会跳过部署。当前源码和工作流都未运行或部署；在全部功能完成并统一检测、首次人工受控部署通过之前，请不要打开自动开关。

达到启用条件后，由有仓库管理员权限的所有者按以下步骤配置：

1. 打开项目GitHub仓库，进入 **Settings → Secrets and variables → Actions**。
2. 在 **Repository secrets** 中分别点 **New repository secret**，添加：
   - `TENCENT_SECRET_ID`：专用于此工作流的腾讯云密钥ID。
   - `TENCENT_SECRET_KEY`：同一密钥的密钥值。只填GitHub Secret输入框，不要发给开发人员或写入仓库。
3. 腾讯云密钥仅授予目标CloudBase环境中读取/回读并更新`catalog-feed`、`client-api`云函数代码所需权限。确认不会对其他生产资源授予无关权限。
4. 在 **Variables** 中点 **New repository variable**，添加`CLOUDBASE_ENV_ID`，值必须是要更新的CloudBase环境ID；先由开发端对照目标控制台和现有函数核实，不要猜测或填显示名称。
5. 首次受控部署通过并由开发端回读目标函数源码、确认目录接口后，再新增变量`HIKING_CATALOG_AUTODEPLOY`，值填写小写`true`。未配置或设为其他值时工作流跳过部署。
6. 打开 **Actions → Refresh public hiking catalog**，在下一次定时运行或由所有者点 **Run workflow** 后查看该次运行记录。只有目录源快照实际变化才部署；查看`Deploy changed catalog snapshots to CloudBase`步骤结果。失败时脚本会尝试回滚已有函数并回读核对；如新函数首次创建失败留下远端函数，按日志给出的名称人工检查，不要直接重复发布。

工作流用GitHub Actions临时运行器安装固定版本CloudBase CLI，并在任务结束后销毁运行器；凭据只通过GitHub Secrets注入。尚未验证该工作流配置、凭据权限或远端部署。具体腾讯云登录参数依据[CloudBase CLI官方CI登录说明](https://cloud.tencent.com/document/product/876/41539)。
